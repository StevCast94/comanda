🎯 Visión

Comanda es un SaaS multi-restaurante: POS, KDS Cocina, y Panel de Meseros. Cada restaurante tiene su ADMIN con correo+contraseña. El ADMIN crea usuarios operativos (COCINA, CAJA, MESERO) con solo usuario+contraseña, sin email. El SUPERADMIN (Stevens) gestiona suscripciones, puede crear/editar/eliminar restaurantes, y recibe tickets de soporte. Escala: comenzar con 2 restaurantes reales, diseñado para decenas.

🔐 Flujo de Login

POST /api/auth/login { email, password } → El backend busca por email → Si encuentra: verifica password con bcrypt → Si no encuentra: busca por username (para usuarios operativos sin email) → Si role = SUPERADMIN o ADMIN → JWT con restaurantId, role, userId → Si role = CASHIER|COOK_1|COOK_2|WAITER|DELIVERY → JWT con todo lo anterior → Frontend: redirige según role a la pantalla correspondiente - ADMIN → /admin/dashboard - CASHIER → /pos - COOK_1, COOK_2 → /kitchen - WAITER → /waiter - DELIVERY → /delivery - SUPERADMIN → /superadmin/dashboard

🛡️ SUPERADMIN Dashboard

Panel exclusivo de Stevens. Ruta: /superadmin

Secciones:

  1. 🏢 Restaurantes: Tabla con todos los restaurantes. Crear, editar, suspender (active=false), eliminar. Ver métricas por restaurante.
  2. 💳 Suscripciones: Estado de suscripción de cada restaurante (TRIAL, ACTIVE, PAST_DUE, CANCELLED). Activar/desactivar.
  3. 🎫 Tickets de Soporte: Los ADMIN de cada restaurante pueden enviar tickets. El SUPERADMIN los ve, contesta, cierra.
  4. 📊 Métricas Globales: Total restaurantes activos, total usuarios, pedidos del día, revenue total.
  5. 📋 Auditoría: Log de acciones críticas (creación/eliminación de restaurantes, cambios de suscripción).

🏢 Aislamiento Multi-Tenant

🔴 REGLA DURA: Todo query Prisma DEBE filtrar por restaurantId. El middleware extrae restaurantId del JWT y lo inyecta en req.restaurantId. NUNCA hacer queries sin este filtro para datos de restaurante.

Patrón en cada ruta:

// Middleware inyecta req.restaurantId automáticamente const items = await prisma.menuItem.findMany({ where: { restaurantId: req.restaurantId, deletedAt: null } })

🚀 Protocolo de Deploy

🟡 Desarrollo: Todo cambio se prueba en local primero. Solo se deploya cuando está verificado.
🟡 Horario: Deploys solo en horario de tráfico mínimo (madrugada GMT-5 o domingo).
🟡 Rollback: Siempre tener el commit anterior identificado para revertir con git revert y push inmediato.
🟡 Commit messages: Descriptivos con prefijo (feat:, fix:, chore:, security:).

🧠 Integración con Matrix

  • El SUPERADMIN ve Comanda como un proyecto más en Matrix Dashboard
  • Las métricas se sincronizan vía Railway Cron Job cada 6h desde comanda.one/api/metrics
  • Los eventos críticos (nuevo restaurante, ticket de soporte, pago) se registran como TimelineEvent
  • Cosmo y Wanda pueden consultar métricas de Comanda igual que cualquier otro proyecto
  • Todos los procesos y protocolos documentados en Matrix → Timeline + Tasks

📋 Procesos Documentados en Matrix

  1. Onboarding nuevo restaurante: SUPERADMIN crea restaurante → asigna plan → entrega credenciales ADMIN
  2. Soporte: ADMIN crea ticket → SUPERADMIN responde → cierre
  3. Actualización del sistema: Desarrollar en local → test → commit → deploy en horario bajo → verificar
  4. Backup y restauración: Automático diario. Restauración manual probada mensualmente.
  5. Escalamiento de incidentes: Si producción cae, rollback inmediato, diagnóstico, fix, redeploy.
  6. Mantenimiento programado: Aviso a restaurantes con 48h de anticipación.

⚠️ Lecciones de Otros Proyectos (No Repetir)

  1. NO usar import.meta.env en frontend: Hardcodear credenciales. Build local → commit dist.
  2. prisma db push > migrate deploy para Railway.
  3. Seed con upsert: Idempotente, se ejecuta en cada deploy.
  4. API keys hardcodeadas en backend si Railway no las expone bien.
  5. Railway Nixpacks lento: Usar RAILPACK o commitear dist/ precompilado + npm install mínimo.
  6. No duplicar servicios: Railway ya cubre hosting + dominio + SSL. No agregar Vercel/Netlify.
